# AI Foreman Revolutionary Roadmap

## Architecture Principle
P0 (Outcome Monitoring) and P2 (Structured Parsing) share a single foundation:
a **Terminal Outcome Engine** that watches terminal output after sends,
classifies outcomes, and extracts structured data. Everything else sits on top.

## Foundation Layer: TerminalOutcomeEngine

### Data Model
```swift
enum TerminalOutcome: String, Codable, Sendable {
    case unknown
    case success       // prompt returned, success markers found
    case failure       // error markers found
    case hung          // no prompt return after timeout
    case needsInput    // password/confirmation prompt detected
    case stillRunning  // long-running task still going
}

struct TerminalOutcomeReport: Identifiable, Sendable {
    let id: UUID
    let terminalID: String
    let sentCommand: String
    let outcome: TerminalOutcome
    let detectedAt: Date
    let summary: String?          // human-readable outcome description
    let parsedOutput: ParsedTerminalOutput?  // structured data from P2
}

protocol ParsedTerminalOutput: Sendable {
    var parserType: String { get }
}
```

### Engine Behavior
- When `sendForemanText` fires, register the terminalID in `outcomeMonitor`
- Poll snapshots at 500ms (vs normal 2s) for monitored terminals
- Compare consecutive snapshots:
  - **Prompt return**: `likelyWaitingForInput` becomes true after being false
  - **Error**: error markers appear in new lines
  - **Success**: success markers (`✓`, `PASS`, `Done`) in new lines
  - **No change for 15s**: classify as hung (unless long-running was expected)
- Stop monitoring when outcome is determined or max timeout (60s)
- Report outcome back to store → activity log → UI → notifications

### Structured Parsers (P2 built-in)
```swift
protocol TerminalOutputParser {
    var commandHints: [String] { get }  // e.g. ["jest", "vitest"]
    func parse(visibleText: String, newLines: [String]) -> ParsedTerminalOutput?
}

struct TestOutput: ParsedTerminalOutput {
    let parserType = "test"
    let framework: String      // "jest", "pytest", "cargo"
    let passed: Int
    let failed: Int
    let skipped: Int
    let durationMs: Int?
    let failedTests: [String]
}

struct GitStatusOutput: ParsedTerminalOutput {
    let parserType = "git"
    let branch: String
    let ahead: Int
    let behind: Int
    let modifiedFiles: Int
    let untrackedFiles: Int
    let isMergeConflict: Bool
}
```

Parsers run automatically during outcome monitoring. Their results feed into:
- Better sidebar summaries ("3 tests failing in auth.spec.ts" instead of raw text)
- Better LLM prompts (structured JSON instead of text soup)
- Better workflow decisions ("tests failed → run fix command → re-run tests")

## Integration Layer: ForemanNotifier (P1)

Thin layer on top of the Outcome Engine:
- Compares current snapshot signals to previous snapshot signals
- Triggers UNNotification on state transitions:
  - `!error → error`: "Build failed in 'api tests'. Retry? View?"
  - `running → !running`: "Tests completed. 42 passed, 3 failed."
  - `!needsInput → needsInput`: "Terminal 'deploy' waiting for input."
- Uses existing `UNUserNotificationCenter` setup in AppDelegate
- Respects DND: no notifications if Ghostty is focused and sidebar is visible

## Application Layer: ForemanWorkflow (P3)

```swift
struct WorkflowStep: Identifiable, Sendable {
    let id: UUID
    let targetTerminalID: String
    let command: String
    let expectedOutcome: TerminalOutcome
    let timeoutSeconds: Int
    let onSuccess: StepTransition     // .next, .finish, .goto(stepID)
    let onFailure: StepTransition     // .retry, .fallback(stepID), .askUser
    let isRisky: Bool                 // requires explicit approval
}

struct ForemanWorkflow: Identifiable, Sendable {
    let id: UUID
    let name: String
    let steps: [WorkflowStep]
    let currentStepIndex: Int
    let status: WorkflowStatus        // .pending, .running, .completed, .failed
}
```

Execution loop:
1. User approves a workflow (generated by LLM or manually built)
2. Execute step N → send command → monitor outcome
3. Outcome matches expected → follow `onSuccess` transition
4. Outcome doesn't match → follow `onFailure` transition
5. Show live progress in sidebar: "Step 2/4: Re-running tests… (monitoring)"

## Intelligence Layer: ForemanContextGraph + ForemanMemory (P4 + P5)

### ContextGraph
```swift
enum TerminalRelationship: Sendable {
    case sameProject          // shared CWD or parent/child directories
    case serviceDependency    // terminal B mentions port used by terminal A
    case processParent        // same process tree
    case conflicting          // e.g. both try to bind same port
}

struct TerminalContextGraph {
    var edges: [(from: String, to: String, relationship: TerminalRelationship)]
}
```

Inferred heuristically from snapshots:
- `sameProject`: CWD overlap
- `serviceDependency`: port mentions in output (regex `localhost:\d+` or `127.0.0.1:\d+`)
- `conflicting`: same port mentioned in launch commands

### Memory
```swift
struct SituationOutcomeRecord: Codable, Sendable {
    let id: UUID
    let situationFingerprint: Int   // hash of snapshot signals + visible text
    let action: String              // command that was sent
    let outcome: TerminalOutcome
    let timestamp: Date
    let terminalContext: String     // CWD, title
}
```

Storage: SQLite via `SQLite3` (built into macOS, no external deps)
Path: `~/Library/Application Support/Ghostty/foreman/memory.sqlite3`

Query: When drafting a response, hash the current snapshot and query for
situation fingerprints within Hamming distance N. Boost suggestions that
succeeded in the past.

## Optimal Implementation Order

### Commit 1: TerminalOutcomeEngine + Parsers (P0 + P2 foundation)
- `TerminalOutcomeEngine.swift` — monitoring, classification, timeout
- `TerminalOutputParser.swift` — protocol
- `TestOutputParser.swift` — jest, pytest, cargo test
- `GitStatusParser.swift` — git status
- Wire into `sendForemanText` and `ForemanSidebarStore`
- Update activity log to show outcomes

### Commit 2: Proactive Notifications (P1)
- `ForemanNotifier.swift` — state transition detection
- Wire into AppDelegate notification center
- Add notification categories and actions

### Commit 3: Goal Workflows (P3)
- `ForemanWorkflow.swift` — model and execution engine
- Update LLM planner prompt to generate workflows
- Sidebar workflow progress UI

### Commit 4: Context Graph + Memory (P4 + P5)
- `TerminalContextGraph.swift` — inference heuristics
- `ForemanMemory.swift` — SQLite persistence
- Sidebar graph visualization (minimal: related-terminal badges)
- Memory-boosted drafting

## Key Technical Decisions

1. **SQLite over Core Data**: Lighter weight, no model migrations needed for simple tables,
   built into macOS, no package dependencies.

2. **500ms post-send polling**: Fast enough to catch quick commands, slow enough to not
   hammer the CPU. Falls back to 2s for idle terminals.

3. **Parser auto-selection**: Parsers declare command hints. The engine runs all parsers
   and takes the highest-confidence result. No need for explicit parser selection.

4. **Workflow generation by LLM**: The planner prompt is updated to optionally return
   a workflow JSON instead of flat drafts. The UI shows a workflow toggle.

5. **Memory similarity**: Use keyword overlap + Jaccard similarity on normalized visible
   text. No embeddings needed for v1 — good enough and zero ML infra.
